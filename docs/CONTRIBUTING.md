## 1. 역할과 개인별 기준

| 팀원 | GitHub | 정리 책임 | Git 실습 기록 담당 | 기본 리뷰 대상 |
| --- | --- | --- | --- | --- |
| 남정현 | @NamJungHyeon | 저장소·권한·main 보호 설정, `docs/CONTRIBUTING.md`, `.github/` 템플릿, README 뼈대 | `git commit --amend` | 유영민의 PR |
| 강소연 | @soy7yos | 충돌 실습 일정, `docs/conflict-resolution.md` | `git reset --soft HEAD~1` | 남정현의 PR |
| 유영민 | @imyoman99 | `docs/troubleshooting-log.md` 구조, `SUBMISSION.md` 취합 | `git revert` | 강소연의 PR |

- `git stash` / `git stash pop`은 세 명이 함께 실습하고 각자의 역할을 기록한다.
- 문서 담당자는 취합과 누락 확인을 책임지며, 다른 팀원의 참여를 대신하지 않는다.
- README 팀원 표에 본인 행과 소개 링크를 추가하는 것은 각 팀원이 자신의 PR에서 한다.

모든 팀원은 다음을 각각 충족한다.

- 본인이 작성한 PR을 **최소 2개** 병합한다.
- 다른 사람의 **서로 다른 PR 2개**에 실질적인 리뷰를 작성한다.
- 본인 PR에서 리뷰 제안을 **최소 1회 수정 커밋으로 반영**하고 커밋 링크와 함께 답글을 남긴다.
- 본인의 팀 소개 파일(`team/<이름>.md`)에 최소 1건의 기여 커밋을 남긴다.
- 최소 1개 트러블슈팅 시나리오의 기록 작성에 참여하고 이름과 역할을 남긴다.

PR 2개는 최소 기준이다. 문서 작업, 충돌 실습, 증빙 보완에 필요하면 PR을 추가로 만든다.

## 2. 저장소 설정

- 저장소: https://github.com/NamJungHyeon/B2-2 (개인 저장소 + Collaborator 초대, 옵션 B)
- 세 명 모두 Write 권한으로 참여한다.
- `main` 브랜치 보호 규칙:
  - PR을 통해서만 병합한다. (직접 push 금지)
  - 작성자 외 **최소 1명의 승인**을 요구한다.
  - 새 커밋이 올라오면 기존 승인을 해제하고 다시 승인받는다. (Dismiss stale approvals)
  - 리뷰 대화가 모두 해결(Resolve)되어야 병합할 수 있다.
  - 관리자도 규칙을 우회하지 않는다. (Do not allow bypassing)
  - `main`의 강제 push와 삭제를 허용하지 않는다.
- 보호 설정 화면은 `docs/evidence/`에 캡처로 저장한다.
- 초기 커밋 이후 모든 변경은 PR로 진행한다.

## 3. 브랜치 전략 (GitHub Flow)

- `main`: 소개 내용과 링크가 정상이며, 충돌 마커나 미완성 변경이 없는 **항상 제출 가능한 상태**.
- `feature/*`: 독립적으로 검토하고 병합할 수 있는 작업 하나.
- `develop`이나 개인별 영구 브랜치는 만들지 않는다.

우리 팀이 GitHub Flow를 선택한 이유:

1. 작업별 브랜치를 사용하면 서로의 미완성 변경을 분리할 수 있다.
2. PR과 리뷰를 통해 변경 이유와 검증 결과를 확인하고 main에 반영할 수 있다.
3. 3명 규모의 문서 프로젝트에서 간단한 절차로 안정적인 main을 유지할 수 있다.

작업 단위를 나누는 기준:

- 서로 목적이 다른 변경은 **별도 Issue와 PR**로 나눈다. (예: 소개 문서 작성과 충돌 실습은 별개)
- 같은 목적의 문서·링크 수정은 하나의 PR에 포함할 수 있다.
- 다른 사람의 브랜치에는 사전 협의 없이 push하지 않는다.
- 브랜치는 미리 만들지 않고 **작업할 때 최신 main에서** 만들며, 병합 후 삭제한다.

## 4. 브랜치 네이밍 규칙

```
feature/<이름>-<작업내용>
```

- `<이름>`: 영문 이름 또는 약칭. 팀에서 쓰는 표기: `Nam`, `sy`, `Min`
- `<작업내용>`: 영문 소문자, 단어 사이는 `-`
- 대소문자는 이름 부분에만 허용하고, 작업내용은 소문자로 쓴다.

| 용도 | 예시 |
| --- | --- |
| 소개 문서 | `feature/Nam-profile`, `feature/sy-profile`, `feature/Min-profile` |
| 협업 문서·양식 | `feature/Nam-github-templates`, `feature/Nam-contributing` |
| 충돌 실습 | `feature/sy-conflict-1`, `feature/Nam-conflict-1` |
| 트러블슈팅 실습 | `feature/Min-troubleshoot` |
| 긴급 수정 | `feature/Nam-hotfix-readme-link` |

## 5. 커밋 메시지 컨벤션

```
<type>: <무엇을 어떻게 변경했는지>
```

- `type`은 영문 소문자, 설명은 한국어를 기본으로 한다.
- 한 커밋에는 하나의 목적을 담는다. 제목 끝에 마침표를 붙이지 않는다.
- 설명이 더 필요하면 빈 줄 뒤 본문에 이유를 적는다.

| type | 사용 기준 | 예시 |
| --- | --- | --- |
| `docs` | 소개·규칙·실습 기록 등 문서 변경 | `docs: 남정현 팀원 소개 문서 추가` |
| `fix` | 잘못된 링크·경로 등 오류 수정 | `fix: README의 강소연 소개 링크 경로 수정` |
| `chore` | 저장소 설정과 협업 양식 관리 | `chore: PR 본문 템플릿과 Issue 템플릿 추가` |
| `feat` | 새 실행 기능 추가 | `feat: 팀원 소개 출력 기능 추가` |
| `refactor` | 동작을 유지하며 코드 구조 개선 | `refactor: 소개 출력 함수 중복 제거` |
| `test` | 테스트 추가·수정 | `test: 소개 출력 결과 검증 추가` |

이 프로젝트에서는 주로 `docs`, `fix`, `chore`를 사용한다. 단순 오탈자는 `docs`로 쓴다.

허용 예시:

```
docs: 리뷰 반영 - 소개 문서에 이번 미션 역할과 학습 목표 추가
docs: README 충돌 해결 과정과 판단 이유 기록
chore: 충돌 실습용 라벨 추가
```

금지 예시 (변경 대상과 내용이 드러나지 않음):

```
update
fix
wip
final
bug fix
docs: 파일 수정
docs: 유영민 팀원 소개 문서 수정2
```

`수정`, `수정2`처럼 **무엇을** 고쳤는지 없는 메시지는 쓰지 않는다. 리뷰 반영 커밋이라면 `docs: 리뷰 반영 - 최애 음료를 구체적인 메뉴명으로 변경`처럼 반영 내용을 적는다.

GitHub의 자동 병합 메시지(`Merge pull request #N ...`)와 `git revert`의 자동 메시지는 예외로 허용하고, 연결된 PR에서 변경 목적을 설명한다.

## 6. Issue 규칙

**모든 작업은 Issue를 먼저 만든다. 충돌·트러블슈팅 실습도 Issue로 등록한다.**

- Issue는 `.github/ISSUE_TEMPLATE/task.md` 양식 하나를 공통으로 사용한다. 충돌·트러블슈팅 실습도 같은 양식으로 만들고, 실습별 기록 항목은 `docs/conflict-resolution.md`, `docs/troubleshooting-log.md`의 형식을 따른다. (실습용 Issue 양식을 따로 두면 기록 문서와 내용이 중복되거나 어긋날 수 있어 두지 않는다.)
- 제목 접두어:

| 접두어 | 용도 |
| --- | --- |
| `[Docs]` | 문서 작성·수정 |
| `[Chore]` | 저장소 설정, 양식, 라벨 |
| `[Fix]` | 링크·경로 등 오류 수정 |
| `[Conflict]` | 충돌 실습 |
| `[Troubleshoot]` | Git 트러블슈팅 실습 |

- 본문에는 목적, 변경할 파일, 완료 조건, 작업 브랜치, 리뷰어를 적는다.
- Assignees에 본인을 지정하고 라벨을 붙인다.
- Issue 1개 = PR 1개를 기본으로 한다.

## 7. PR 규칙

- PR 제목은 커밋 메시지와 같은 형식을 쓴다. 예: `docs: 남정현 팀원 소개 문서 추가`
- 본문은 `.github/pull_request_template.md`가 자동으로 채워 준다. 항목을 지우지 않는다.
  - **연결 이슈**: `Closes #번호` (제목이 아니라 본문에 쓴다. 이슈 2개면 `Closes #3` / `Closes #4` 각각 쓴다)
  - **변경 사항 (What)**: 어떤 파일의 무엇을 바꿨는지
  - **변경 이유 (Why)**: 왜 필요한지, 이슈의 어떤 완료 조건을 해결하는지
  - **검증 방법과 결과 (How)**: 실제로 확인한 방법과 결과
  - **확인 사항**: 체크리스트. 해당 없는 항목은 지우지 말고 체크 후 이유를 적는다.
- Reviewers는 `.github/CODEOWNERS`에 따라 자동으로 지정된다. 지정되지 않은 경로면 순환 규칙에 따라 직접 지정한다. 부재 시 나머지 팀원이 대신한다.
- PR 사이드바 **Development**에 이슈가 연결됐는지 확인한다.

병합 조건:

- 작성자는 자신의 PR을 승인하지 않는다.
- 다른 팀원의 실질적인 리뷰 → 작성자의 응답 → 필요한 수정과 재검증 → **최소 1명의 승인** → 모든 대화 Resolve.
- 병합 방식은 **Create a merge commit**으로 통일한다. (squash/rebase 금지 — `git log --graph`에 브랜치 흐름을 남기기 위해)
- 병합 후 **Delete branch**를 누르고, 로컬 브랜치도 삭제한다.

## 8. 코드 리뷰 규칙

### 리뷰어

- 각 PR에 **파일이나 문장을 근거로 한** 질문, 개선 제안, 대안, 문제 지적을 **최소 1개** 작성한다.
- `LGTM`, `좋아요`, `확인했습니다`만 작성한 것은 실질적인 리뷰로 세지 않는다. 승인 시에는 코멘트를 따로 남긴 뒤 `확인했습니다.`로 Approve해도 된다.
- 코멘트 앞에 우선순위를 붙인다.

| 접두어 | 의미 | 예시 |
| --- | --- | --- |
| `[P1] Must:` | 병합 전 반드시 수정 | `[P1] Must: team/min.md 12행에 충돌 마커가 남아 있습니다.` |
| `[P2] Recommend:` | 고치면 좋음. 작성자가 이유를 설명하고 반영하지 않을 수 있음 | `[P2] Recommend: 문서 간 표기 통일을 위해 백틱을 제거해 주시면 좋을 것 같습니다.` |
| `[P3] Question:` | 질문, 단순 의견 | `[P3] Question: "깊생하기"가 어떤 뜻인지 궁금합니다.` |

- 승인 이후 새 커밋이 올라오면 다시 확인하고 승인한다.
- 횟수를 채우기 위해 일부러 오류를 넣지 않는다. 실제로 도움이 되는 피드백을 주고받는다.

### 작성자

- 코멘트마다 **답글 또는 수정으로 반드시 응답**한다.
- 반영한 경우 **커밋 해시 또는 커밋 링크**와 변경 내용을 답글에 남긴다.
  - 좋은 예: `반영했습니다. d06883b 커밋에서 문서 전체의 백틱을 제거했습니다.`
  - 부족한 예: `수정했습니다.` — 어느 커밋에서 무엇을 고쳤는지 추적할 수 없어 증빙이 되지 않는다.
- 반영하지 않기로 했으면 이유를 적고 리뷰어와 합의한다.
- 라인 코멘트는 응답 후 **Resolve conversation**을 누른다.

### 순환 리뷰

기본 순환은 **남정현 → 유영민 → 강소연 → 남정현** (화살표 방향이 "누구의 PR을 리뷰하는가")이다.

| 작성자 | 리뷰어 |
| --- | --- |
| 남정현 | 강소연 |
| 유영민 | 남정현 |
| 강소연 | 유영민 |

이 규칙은 `.github/CODEOWNERS`에 파일별로 반영되어 있어, 해당 파일이 바뀐 PR에는 리뷰어가 자동으로 지정된다.
두 번째 PR에도 같은 순환을 적용하면 각자 다른 사람의 PR 2개를 리뷰하게 된다. 최종 개인별 횟수는 `SUBMISSION.md`에서 확인한다.

## 9. 작업 순서 (명령 예시)

1. GitHub에서 Issue를 만든다. (양식 사용)
2. 최신 main에서 브랜치를 만든다.

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/Nam-contributing
```

3. 파일을 작성하고, 올릴 파일만 골라서 커밋한다.

```bash
git status
git diff
git add docs/CONTRIBUTING.md
git commit -m "docs: 협업 규칙 문서 작성"
git push -u origin feature/Nam-contributing
```

4. GitHub에서 PR을 만든다. (base: `main`, compare: 작업 브랜치, 본문에 `Closes #번호`, Reviewers 지정)
5. 리뷰 코멘트를 받으면 **같은 브랜치에서** 수정하고 push한다. PR에 자동으로 커밋이 추가된다.

```bash
git add docs/CONTRIBUTING.md
git commit -m "docs: 리뷰 반영 - 브랜치 네이밍 예시에 실습 브랜치 추가"
git push origin feature/Nam-contributing
```

6. 코멘트에 커밋 링크와 함께 답글을 남기고 Resolve한다.
7. 리뷰어가 다시 확인하고 Approve하면 **Create a merge commit**으로 병합하고 브랜치를 삭제한다.
8. 로컬을 정리한다.

```bash
git switch main
git pull --ff-only origin main
git branch -d feature/Nam-contributing
```

원격에 있는 브랜치가 로컬에 안 보이면 `git fetch origin` 후 `git switch <브랜치>`로 가져온다.

## 10. 충돌 대응 흐름

```
발생 사실 공유 → 당사자 의도 확인 → 해결안 합의 → 수정·검증 → 커밋·PR → 문서 기록
```

| 단계 | 누가 | 어떻게 | 어디에 |
| --- | --- | --- | --- |
| 공유 | 충돌을 만난 사람 | 팀 채팅 또는 PR 코멘트에 브랜치·파일·영역을 알린다 | PR |
| 의도 확인 | 양쪽 작성자 | 각자 그 부분을 왜 그렇게 바꿨는지 설명한다 | PR 코멘트 |
| 합의 | 양쪽 작성자 | keep both / choose one / 새로 작성 중 선택하고 이유를 남긴다 | PR 코멘트 |
| 수정·검증 | 충돌을 만난 사람 | 마커를 제거하고 링크·표 렌더링을 확인한다 | 로컬 |
| 커밋·PR | 충돌을 만난 사람 | `docs: main 병합 충돌 해결 - README 팀 소개 문장`처럼 커밋 | PR |
| 기록 | 강소연 (취합), 참여자 | 사례별 기록을 남긴다 | `docs/conflict-resolution.md` |

충돌을 재현할 때는 커밋되지 않은 변경이 없는지 먼저 확인하고 main을 반영한다.

```bash
git fetch origin
git merge origin/main
```

충돌 마커의 의미:

- `<<<<<<< HEAD` 아래: 현재 체크아웃한 브랜치의 내용
- `=======`: 두 내용의 경계
- `>>>>>>> <브랜치명>`: 병합해 오는 쪽의 내용

한쪽을 무조건 선택하지 않고 **사실의 정확성, 양쪽 변경 목적, 중복 여부, 링크와 문서 일관성**을 기준으로 최종 내용을 정한다.

실습 계획:

- 실습 1: 남정현·강소연, 실습 2: 강소연·유영민.
- 같은 기준 커밋에서 브랜치 2개를 만들고 README의 **같은 문장**을 다르게 수정한다. 한 PR을 먼저 병합하고 다른 브랜치에서 최신 main을 병합하면 같은 영역의 충돌이 재현된다. (비자명 충돌 기준 충족)
- 실습 2는 실습 1 해결 이후의 main에서 새로 시작하고 별도 사례로 기록한다.
- `docs/conflict-resolution.md`에는 사례마다 참여자와 역할, 브랜치·기준 커밋·파일·영역, 재현 순서와 명령, 충돌 마커 원문, 선택한 해결안과 이유, 해결 후 내용과 검증 결과, PR·커밋 링크, 예방 방법과 배운 점을 적는다.
- 충돌 마커는 기록 문서의 코드 블록 안에만 남기고, 실제 소개 문서나 README에는 남기지 않는다.

## 11. Git 트러블슈팅 실습

| 시나리오 | 담당 | 실습 범위와 확인 내용 |
| --- | --- | --- |
| `git commit --amend` | 강소연 | push하지 않은 최근 커밋 메시지를 수정하고 전후 메시지를 확인 |
| `git reset --soft HEAD~1` | 유영민 | 로컬 실습 커밋을 취소하고 변경이 스테이징에 유지되는지 확인 |
| `git revert <커밋ID>` | 유영민 | 작업 브랜치에 push한 실습 커밋을 새 커밋으로 되돌리고 다시 push해 기존 기록이 유지되는지 확인 |
| `git stash` / `git stash pop` | 남정현 | 추적 중인 파일을 수정해 보관하고 브랜치를 전환했다가 돌아와 복원되는지 확인 |

주의:

- `amend`와 `reset`은 **공유하지 않은 로컬 실습 커밋**에만 사용한다.
- `amend`/`reset`의 전후 상태는 히스토리에서 사라지므로 실행 전후 `git log --oneline -3` 출력을 텍스트나 스크린샷으로 남긴다.
- `revert`는 실제 소개 내용이 아니라 실습용 변경을 대상으로 한다.
- `stash`는 기본적으로 새 미추적 파일을 보관하지 않으므로 추적 중인 파일로 실습한다. pop에서 충돌이 나면 해결 후 남은 stash를 처리한다.
- main에서 실습하지 않는다.

`docs/troubleshooting-log.md`의 각 기록에는 **참여자·역할, 상황, 실행 전 브랜치·상태, 재현 절차와 명령, 실행 후 결과, 주의점, 선택 이유, 증빙**을 고정 항목으로 둔다.

## 12. 예외 상황 대응

**긴급 수정**
최신 main에서 `feature/<이름>-hotfix-<내용>` 브랜치를 만들고 필요한 수정만 한다. 검증 → PR → 다른 팀원의 신속한 리뷰·승인 → 병합 순서를 따른다. 급하더라도 main 보호를 우회하지 않는다.

**의미 없는 커밋 메시지를 이미 push한 경우**
공유된 커밋은 amend/rebase/강제 push로 고치지 않는다. PR 제목과 본문에 변경 의도를 보완하고, `docs/troubleshooting-log.md`에 실수와 개선 조치를 남긴다. 예방을 위해 push 전에 `git log --oneline -3`으로 메시지를 확인한다.

**반복 충돌**
같은 파일에 작업이 몰리는지, 담당 범위가 겹치는지, 브랜치가 오래 유지되는지 확인한다. 소개 본문은 개인 파일로 분리하고, README 편집은 순서를 조율하며, 작은 PR을 자주 병합하고 작업 브랜치에 최신 main을 반영한다.

**rebase (선택 보너스)**
`rebase`는 커밋을 다시 만들어 커밋 ID를 바꾼다. 개인 브랜치에서만 정리하고 전후 기록을 남긴다. main에는 적용하지 않으며, push한 브랜치의 재작성은 팀 합의 없이 하지 않는다.
